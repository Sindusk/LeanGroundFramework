# package: cut an Initiative

Only once the owner has placed it in Work-Ready.

1. Read its block: `python tools/docs.py "<Initiative>"`, then the design sections it names. **Count before cutting:** a sizing claim is a guess until the code seams are read; where no code exists yet, count the files each package will create. **What a block says of existing code is read, never inferred,** absences too [PF-599, PF-673].
2. Ask the owner the granularity (saying what a finer cut buys), each package's builder and any reviewer; wait. Where the Initiative print ends `forks: decide`, take the recommended granularity and builders as defaults, each with its alternatives, leading the report and commit body [PF split rulings 2026-11-15]. Delegating a cut: ask first, then cut one package at a time on `model: "sonnet"`, passing on the next ID and seams.
   **Rule attack**, once the owner has answered: where the rules a cut builds meet two or more other systems, one Agent call before cutting, `model: "sonnet"`, read-only, given the section numbers and those systems: "List the situations these rules leave undecided or decide two ways, at most 200 words, no fixes, [T] where two readings make tests assert different outcomes." Each real gap is a question (step 6); the cut commit's body counts those returned and those raised [PF-537]. The build's attack (`SKILL.md` step 4) takes one package's exact text.
3. Each package is an id from the ledger's stated next free number (bump it; never reuse a retired one; no `XX-117a`: an item needing its own status is a peer package). Ledger line: `  - XX-n Name (Claude <model>) — <status>`, plus `, reviewed by Claude <model>` if the owner asks. A build is never reviewed by its own model.
4. Each package's block, as `- **XX-n Name.**` in its Initiative's block, states in order:
   *Outcome:* one sentence · *Done when:* observable criteria · *Touches:* design sections, then code seams: files and functions to change, the test files joined, the helpers and conventions used · *Depends on:* · *Migration:* what existing data or users need, normally "none" before release · *Verify:* the tests, then the manual check, if any, with the state it needs; each manual step reachable with the shipped data, else the test that shows it; never "the owner runs" [MM-102] · *Scope:* "no open owner decision", or the question that decides it · *Size:* the novel seams and why it is one boundary.
   The rules it implements must already be in `DESIGN.md`; a block cites design sections, never a working document. Each input the Outcome names exists, else the block names the gap and its fill; a user-visible stand-in is the owner's decision at the cut [AZ-191]. The Initiative's block opening names the shared fixtures and any ordering between packages that touch the same files.
   **Check before naming** each outside fact against the real thing: a third-party command in its source [MM-110], where a config file lands [MM-121], what a dependency registers [MM-142], a copied file's own licence header [MM-144], a file format against a real saved file [MM-106].
5. **Oversized** (split it, or justify in one line): the outcome needs "and" to join two results each worth shipping alone; it crosses more than one novel seam (the first of a kind: a route, screen, table, message type, data format or integration; rows along a solved seam don't count), each one needed; one reviewer couldn't hold its diff; or more than about five deliverables with no reason.
6. Design-choice gaps become questions in `DESIGN.md` 6.2 (the lg-design skill, "Raise"), the lines waiting on them say so, and the report names a round as the next step. Gaps routine enough for the builder go in the block's *Scope* as "builder decides: …".
7. Add blocks with `python tools/docs.py ledger insert <file> --after XX-n` or in place, run `check`, and commit docs-only: `Cut <Initiative> into Work Packages`, body naming each package and the questions raised.
