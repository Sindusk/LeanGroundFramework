# package: cut an Initiative

Only once the owner has placed it in Work-Ready.

1. Read its block: `python tools/docs.py "<Initiative>"`, then the design sections it names. **Count before cutting:** a sizing claim is a guess until the code seams are read; where no code exists yet, count the files each package will create.
2. Ask the owner the granularity (saying what a finer cut buys), the builder per package and any reviewer. Wait for the answer. Delegating a cut: ask first, then cut one package at a time on `model: "sonnet"`, passing on the last cut's next ID and seams.
   **Rule attack**, once the owner has answered: where the rules a cut builds meet two or more other systems, one Agent call before cutting, `model: "sonnet"`, read-only, given the section numbers and those systems: "List the situations these rules do not decide, or decide two ways, at most 200 words; no fixes. Mark with [T] each one where two readings would make a test assert different outcomes." Each real gap is a question (step 6); the cut commit's body says how many came back and how many became questions [PF-537].
3. Each package is an id from the ledger's stated next free number (bump it; never reuse a retired number; no hierarchy below a package, so no `XX-117a`: an item needing its own status becomes a peer package). Ledger line: `  - XX-n Name (Claude <model>) — <status>`, plus `, reviewed by Claude <model>` if the owner asks. A build is never reviewed by its own model.
4. Each package's block, as `- **XX-n Name.**` in its Initiative's block, states in order:
   *Outcome:* one sentence · *Done when:* observable criteria · *Touches:* design sections, then code seams: the files and functions to change, the test files the tests join, and the helpers and conventions they use · *Depends on:* · *Migration:* what existing data or users need, normally "none" before release · *Verify:* the tests, then the manual check, if any, with the state it needs; each manual step must be reachable with the shipped data, else name the test that shows it · *Scope:* "no open owner decision", or the question that decides it · *Size:* the novel seams and why it is one boundary.
   The rules it implements must already be in `DESIGN.md`; a block cites design sections, never a working document. The Initiative's block opening names the shared fixtures and any ordering between packages that touch the same files.
5. **Oversized** (split it, or justify in one line): the outcome needs "and" to join two results each worth shipping alone; it crosses more than one novel seam (the first of a kind: a new route, screen, table, message type, data format or integration; rows along a solved seam don't count); one reviewer couldn't hold its diff; or more than about five deliverables with no reason. Check each named novel seam is needed.
6. Gaps the cut finds that are design choices become questions in `DESIGN.md` 6.2 (the design skill, "Raise"), and the lines that wait on them say so; the cut's report tells the owner the next step is a round for them. Gaps routine enough for the builder go in the block's *Scope* as "builder decides: …".
7. A block is added with `python tools/docs.py ledger insert <file> --after XX-n` or written in place; then `python tools/docs.py check`; commit docs-only: `Cut <Initiative> into Work Packages`, body naming each package and the questions raised.
